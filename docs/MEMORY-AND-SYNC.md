# 记忆与双链路同步（v0.1 草案）

> 依据：需求方 2026-11-12 决策 —— 核心机的工作 LLM 与角色 LLM **不再依赖 PC**，设备侧独立运行；
> **显现模式**由 PC 通过 HTTP 提供页面，且自带 LLM 链路；**角色只有一个**，两条链路必须共享记忆，
> 显现模式产生的记忆要回流设备侧。
> 关联：`WORLD-CORE-SPEC.md` §5/§6/§7、`PROJECT-PLAN.md` §2.7 / §9 / §10。

---

## 1. 两条链路，一个角色

| | 设备链路（核心机） | PC 链路（显现） |
|---|---|---|
| 页面 | 本地壳 `127.0.0.1:8080`（**常驻，不导航**） | PC 提供，**iframe 内嵌**（P1 已定） |
| LLM | 设备直连云端（工作层 + 角色层） | OLVT 自带链路 |
| TTS / Live2D | 无（A15：离线不发声） | 有 |
| 产出 | 生活事件、独白、剧情/背景、气泡 | 语音对话、表情、对话历史（**全部由 PC 完成**） |
| 权威数据 | 生活事件、心情、作息 | 记忆 L0–L3、对话历史 |

**角色唯一性靠三件事保证**：
1. **同一份人格文件**（`persona/`，版本化，两端同源）；
2. **同一份事实记忆**（PC 权威，设备只读缓存）；
3. **说话权互斥**：显现打开期间，设备角色层 LLM 静音（只记 `trace`，不产生气泡/独白），由 PC 链路说话；关闭后设备恢复。

**显现期间的设备职责只有两条**：继续生活 tick（`trace`）、把记忆推给 PC；结束后接收 PC 产生的记忆。UI / Live2D / TTS / ASR / 对话 LLM 全部在 PC。

> 不做"两套脑子各说各话"：设备链路在显现期间只做"生活与观察"，不做表达。

## 2. Q1 定稿：设备只存文本，向量在 PC

| 层 | 存在哪 | 形式 | 谁写 |
|---|---|---|---|
| 原始事件 | 设备 IndexedDB | `{seq, uuid, t, kind, payload}` 文本 | 设备 |
| 事实（fact） | 设备缓存 + PC 权威 | `{s,p,o,t,conf,tier,supersedes}` 文本 | 设备归纳候选 → PC 定稿 |
| 向量 | **仅 PC** | `vec0`（sqlite-vec） | PC |
| 全文索引 | 设备（本地）+ PC（FTS5） | 倒排（bigram） | 各自 |
| 摘要 / 日记 | PC 权威，设备缓存 | 纯文本 | PC（LLM） |

**设备侧检索**：字面（bigram 倒排）+ 时间衰减 + 关键词触发；**不做 KNN**。
**语义检索**：PC 在线时转发 `memory:query`；离线时降级为本地字面检索，并在结果里标注 `semantic:false`。

**为什么**：设备 2GB 内存，embedding 模型（34MB）+ WASM 运行时（+40–60MB）与渲染争内存；向量化是批处理任务，天然适合 PC。设备只保留"能离线回忆"的最小集合。

**代价（写清）**：离线时"京都看枫叶"这类语义召回会退化为字面命中；缓解手段是**关键词表 + 事件标题规范化**（写入时就把事件压成"时间 + 地点 + 动作 + 对象"的可检索文本）。

### 2.1 PC 侧向量处理要求（PC AI 必读）

设备**不做**向量化；PC 侧必须承担以下工作（接口见 `PC-INTEGRATION.md` §5）：

| 步骤 | 要求 |
|---|---|
| 接收 | `facts:candidates` / `events:batch`；按 `uuid` 幂等 |
| 规范化 | 时间统一 `Asia/Shanghai`；文本压成"时间 + 地点 + 动作 + 对象" |
| 去重 | 文本哈希 + 时间窗 + `uuid`；同义改写不重复入库 |
| 合并 | LWW（`updated_at`，`pc > device`）；`supersedes` 保留旧事实 |
| 归纳 | 设备已归纳则跳过；否则批量抽取（会话末/每 2h） |
| 向量化 | 本地 `fastembed` + `bge-small-zh-v1.5`（约 90MB，随包预置）或云端 embedding；**禁止运行时下载模型** |
| 落库 | `mem_meta` + `vec0` + FTS5（`tokenize='trigram'`）同库同事务 |
| 回执 | `facts:ack {accepted, merged, rejected}` |
| 查询 | `memory:query` → `memory:result`，目标 ≤200ms，`semantic:true` |
| 回流 | 显现后 `memory:facts` 增量下发（`since` 游标），只发 fact + 摘要 |
| 重建 | 删 `vec0`/FTS5 后可由 `mem_meta` 正文重灌 |

**验收**：10 条 A9 样本（含"7 天前"与同字面旧记忆）top1 命中；索引可重建；模型离线可用。

## 3. 写入路径（设备 → PC）

```
设备事件 ──规则预筛──► 候选（每 20 条或 2h）
        ──设备 LLM 归纳（工作层，JSON schema）──► fact 候选
        ──outbox──► PC：去重（规范化文本哈希 + 时间窗）
                    ├─ 冲突：LWW（updated_at，pc>device）
                    ├─ 向量化（bge-small / 供应商 API）
                    └─ 落 memory.db（L0–L3）
        ◄──ack（含 fact id 与最终文本）── 设备更新缓存
```

- 设备归纳**可选**：预算不足时只上传原始事件，由 PC 归纳。
- 设备不写 L0–L3 定稿，只写"候选"；PC 是唯一定稿方。

## 3.5 显现开始前：设备 → PC 的记忆推送

显现打开时（iframe 加载前），设备通过 WS 推送一次增量：

```js
{ type: "memory:push", since: <last_pushed_seq>,
  facts: [...],            // 设备归纳的候选事实（未定稿）
  events: [...],           // 近 24h 生活事件（摘要级）
  mood: {...}, phase, weather, place }
```

PC 收到后并入自己的上下文（被动块），保证"显现里的她"知道这几天发生了什么。推送失败不阻塞显现（PC 用最后同步点）。

## 4. 回流路径（PC 显现 → 设备）

```
显现会话结束（或每 10 轮）
  PC：抽取 fact（复用 M8-T4 管线）
     ├─ 写入 memory.db
     └─ 下发 `memory:facts` → 设备并入缓存（只读）
  设备：写入事件 `kind:'conversation_summary'`（摘要文本，不含逐句）
```

**为什么不让设备直接读 PC 的 IndexedDB**：显现页面是 PC 的源（跨域），设备无法访问其存储；回流必须走网络。

**回流的粒度**：只下发 **fact + 一段摘要**，不下发逐句对话（避免设备侧"回放昨天情绪"的问题，与 WakeTrace 的 `fact/content` 双通道原则一致）。

## 5. 冲突与幂等

| 场景 | 规则 |
|---|---|
| 同一 fact 两端都有 | 规范化文本哈希相同 → 合并，保留 `conf` 高者 |
| 同一 fact 内容不同 | LWW（`updated_at`），同时间戳 `pc > device` |
| 设备离线期间 PC 新增 | 设备上线后拉增量（`since` 游标） |
| 设备事件与 PC 事件同 uuid | 丢弃（幂等） |
| 删除 | tombstone，30 天后清理 |

## 6. 设备侧存储预算

| 项 | 上限 | 说明 |
|---|---|---|
| 事件 | 2000 条（环形） | 约 1–2MB |
| fact 缓存 | 5000 条 | 约 3–5MB |
| 字面索引 | 5000 文档 | ≤10MB |
| 摘要/日记 | 365 条 | 约 100KB |
| 资产 | 500MB（LRU） | 场景/背景/剧情 |

## 7. 接口（设备 ↔ PC）

| 消息 | 方向 | 载荷 |
|---|---|---|
| `memory:facts` | PC → 设备 | `{since, facts[], summary}` |
| `memory:query` | 设备 → PC | `{text, k, since}` |
| `memory:result` | PC → 设备 | `{hits[], semantic:true}` |
| `facts:candidates` | 设备 → PC | `{facts[], events[]}` |
| `facts:ack` | PC → 设备 | `{accepted[], merged[], rejected[]}` |
