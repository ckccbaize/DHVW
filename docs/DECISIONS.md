## ★D1 核心机跑在哪

**具体问题**：核心机崩溃时，你接受"整页重载（约 1.5–3s 画面重建）"吗？

| 选项 | 具体形态 | 代价 | 收益 |
|---|---|---|---|
| ① 浏览器 Worker | `core.worker`，postMessage 通信（<1ms） | 内存 +30–40MB；崩溃=页面重载；与渲染共享进程 | 0 新进程、0 新部署件；XState/MiniSearch 直接可用 |
| ② 独立进程（Go 单文件） | systemd 单元 + 本地 socket/WebSocket（+2–5ms） | 内存 +15–25MB；多一个部署件与日志；状态机/索引要换 Go 生态重写（XState 不可用） | 核心机可单独重启，渲染不受影响；内存更可控 |
| ③ PC 侧 | — | 主机不在即停摆 | 违背设备自治（A13） |

**影响**：批次 2 的骨架写法、批次 3–7 全部模块、部署项 D1–D5。
**建议**：①。先做批次 1 的**真机内存基线**（J1 提前），若 Chromium 基线 >1.2GB 再评估②（+1 周）。
**要你确认**：① 能否接受页面重载？② 是否现在就要求"核心机独立重启"？

## ★D2 端侧能否直接调 LLM

**具体问题**：PC 不在时，她应该"继续写新剧情/新地图"，还是"只用模板短句过日子"？

| 选项 | 具体规则 | 成本 | 风险 |
|---|---|---|---|
| ① 默认关 + 超时才开 | 主机不可达 > 6h 且用户在 GUI 授权后，才允许受限直连；日 ≤2k output tokens；失败不重试 | 一次剧情 ≈200–400 output tokens；日 6 次 ≈2.4k ≈ ¥0.01–0.02/天，月 <¥1 | key 存设备（需受限 key + 可远程吊销 + 不进日志） |
| ② 只走 PC | 主机不在 = 0 token，只有状态机 + 文法模板 | 0 | 长时间离线内容重复感强 |
| ③ 设备常开 | 24/7 都有 LLM | 同上量级，但不可控 | 与 A16「0 token」验收口径冲突，需改验收 |

**影响**：批次 5（LLM 客户端/预算账本）、批次 6（子 Agent）、A16 验收口径、`DEVICE-DESIGN.md` §8 的"0 token"表述。
**建议**：①。若选②，A16 的"0 token"原样保留；若选③，A16 必须改成"程序化路径 0 token，LLM 路径按账本核算"。
**要你确认**：① 是否接受"设备上有云端 key"？② 超时阈值用 6h 还是别的？

## ★D3 状态机选型

**具体问题**：世界状态机预计 8–12 个状态、3 条并发线（生活 / 生产 / Agent 管理）。你需要"状态图可视化 + 崩溃后快照恢复"吗？

| 选项 | 体积 | 能力 | 代价 |
|---|---|---|---|
| ① XState v5 | 14.2KB gzip（Bundlephobia 实测） | actor 监督、`getPersistedSnapshot()`、可画状态图 | 学习/调试成本中等；需引入依赖 |
| ② 纯 reducer | 0 | 完全可控，现有 `life.worker` 就是这个形态 | 监督/快照要自己写（约 150 行） |
| ③ robot3 | ~2KB | 极简 FSM | 无 actor 监督、无快照 API |

**影响**：批次 2–3 全部状态代码；后续所有"崩溃恢复"验收。
**建议**：W2 用 **3 天**做同一状态图的 ①② 两版，按"快照恢复代码量 + 单测可读性"定；默认①。
**要你确认**：是否接受多一个 14KB 依赖？是否要求状态图可视化？

**影响**：批次 4（记忆模块）、A9/A13 验收、内存预算。

## D12 缩放策略

**具体问题**：720p 设备上，你接受 640×480 画面（k=1，四周大黑边），还是允许 1.5× 非整数缩放（像素大小不均但填满更多）？

| 选项 | 1080p | 720p |
|---|---|---|
| ① 固定 2× 整数 | 1280×960 居中 | 640×480 居中（很小） |
| ② 自适应取整 | k=2 → 1280×960 | k=1 → 640×480；可配 k=1.5 |
| ③ 拉伸填满 | 变形 | 变形 |

**建议**：②，720p 允许 k=1.5（最近邻，仍锐利）。
